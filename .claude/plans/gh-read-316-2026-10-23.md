## 3. The change

**Sandbox (judges).** `config/routing.json`: add `"network": true` to `plan-judge-sol` (~line 20) and
`plan-judge-astra` (~line 38). `scripts/paths.sh` `words()` (~723-725): for a seat with `sandbox == "read-only"` and
`network`, `sandbox` renders nothing and `network` renders
`-c permissions.ghread.extends=":read-only" -c permissions.ghread.network.enabled=true -c default_permissions="ghread"`
(one-line comment: `--sandbox` would override the profile). Any other `network` keeps today's
`sandbox_workspace_write.network_access=true`. `readonly` in `resolve()` (~741) is unchanged: still `.sandbox ==
"read-only"`, so the read-only spec check in seat.sh (~270) still runs for judges. No Codex `config.toml` write (314
and 315 own that file).

**Probe.** The probe is built from the resolved seat, not the caller. `resolve()` adds `probe`: `{env, argv}`.
- `env`: the seat's own environment words that reach its shell: `CODEX_HOME` (codexHome, so `codex sandbox` reads the
  seat's Codex home), Claude `shellEnv` (the `env` words at ~712-716). For a Claude seat `pp_gh_read` also merges the
  `env` maps Claude Code applies to its shell: `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/settings.json`, then the target
  checkout's `.claude/settings.json` and `.claude/settings.local.json` (later wins). With `--new` (a plan seat's
  first launch, no worktree yet) the checkout's two files are replaced by local main's tracked one,
  `git -C "$PP_MAIN" show main:.claude/settings.json`: `pp_worktree_new` (`scripts/paths.sh:845`) cuts the worktree
  from that commit, and the `settings.local.json` that `worktree-setup.sh` then writes holds only Commandeck's
  compact-window, cache and cut keys, none of which gh reads.
- `argv`, Claude: `gh repo view --json nameWithOwner`. Codex: `codex sandbox` + the seat's sandbox words as `codex
  sandbox` takes them (`-c sandbox_mode="<mode>"`, or the two `permissions.ghread` words and `-P ghread`) + `--` +
  `env <shellEnv K=V...>` + the same gh read. The Codex seat gets `shellEnv` through `shell_environment_policy`, whose
  default excludes drop host `*KEY*`/`*SECRET*`/`*TOKEN*` variables; the Builder measures whether `codex sandbox`
  applies that policy (evidence file), and if it does not, the probe also unsets those host variables (`env -u`)
  before adding `shellEnv`, so a host `GH_TOKEN` cannot pass a seat that never sees it.

New `pp_gh_read [--host] [--new] <role> <dir> [effort] [model]` in `scripts/paths.sh` (beside `pp_route`, ~1071): `<dir>` is
the seat's target checkout; with no `origin` remote there it fails `no GitHub remote in <dir>`. Runs the probe in
`<dir>` (so gh resolves the target repo from that checkout's remote) with `timeout 20`; `--host` runs the same gh
read and seat env outside any sandbox (the review hand-in route, section below). On failure prints one reason and the
first error line, returns 1. Reasons, from the probe's stderr and exit:
- `no gh on PATH` (exit 127);
- `no network in the sandbox` (`error connecting`, `could not resolve host`);
- `no credentials visible in the sandbox` (gh asks to log in inside a sandbox while host `gh auth status` passes);
- `not signed in to gh` (gh asks to log in, host too);
- else `gh read failed`.

**Launch refusal.** `scripts/seat.sh` after ~251. Target checkout: `$WT`. When `$WT` does not exist yet (only a plan
seat's first launch with no `COMMANDECK_SEAT_REPO`; line 112 refuses every other missing worktree), the probe runs
`--new` in `$PP_MAIN`, not the caller's `$ROOT` (line 62, whatever branch the caller is on): the worktree is cut from
local main at ~302, after this check, so the probe reads main's remote and main's tracked settings, and a refused
launch leaves no worktree behind. With `COMMANDECK_SEAT_REPO`, `$WT` sits in that repo's workspaces (line 69) and the
probe reads that repo.
`GH_NEW=; GH_DIR=$WT; [ -d "$WT" ] || { GH_NEW=--new; GH_DIR=$PP_MAIN; }`, then
`pp_gh_read ${GH_NEW:+"$GH_NEW"} "$ROLE" "$GH_DIR" "$LEFFORT" "$LMODEL" || { echo "BLOCKED: $ROLE cannot read GitHub from its sandbox: <reason>. Fix: <per reason>" >&2; exit 2; }`.
Opens no pane and writes no record. No fallback, no flag.

**Review pass.** `scripts/builder-codex-pass.sh`. One function, `review_gh_check`, called in `--preflight` (~696) and on
the normal launch path right after the Builder-worktree check (~710), before any prompt or reviewer starts, whatever
the brief holds (no `Closes:` line needed):
- Claude profile: `pp_gh_read codex-reviewer "$WT"`: the reviewer's own shell is unsandboxed, so this is the read it
  will make. Its launch (~1006) gains `Bash(gh issue view:*),Bash(gh pr view:*),Bash(gh pr checks:*)` in
  `--allowedTools`: read-only subcommands, no `gh api` (it can write). `GUIDANCE` (~109) gets one sentence for this
  profile: read issues, linked issues and PR checks/labels with those three commands, `-R <nameWithOwner>`.
- Codex profile: the companion's sandbox cannot be changed, so the check is `pp_gh_read --host codex-reviewer "$WT"`,
  named in its refusal and in doctor as the host hand-in route, never as sandbox access. In the prompt assembly (where
  `NOTE` is built, ~915) the pass appends, read on the host now: each `Closes: #N` issue with `--comments`; each issue
  that issue's body and comments link (`#M`, `owner/repo#M`; one level); the unit branch's PR `state,labels,
  statusCheckRollup` (`no pull requests found` reads as "no PR for this branch"). `GUIDANCE` gets one sentence: gh has
  no network in this sandbox; the GitHub reads below were made on the host at launch; a GitHub read you need that is
  not below is `BLOCKED: GitHub read failed: <command>: no network in the review sandbox` on a line of its own.
- Any failed check or hand-in read refuses the pass with the reason and starts no reviewer. A reviewer reply holding a
  `BLOCKED: GitHub read failed:` line makes the session parse (~307) refuse the pass, quoting that line, instead of
  reading it as a verdict.

**Main restart.** `hooks/lib/context-clear-restart.sh`, before the `terminal create` (~34):
`why=$(pp_gh_read orchestrator "$PP_MAIN" 2>&1) || { rm -f "$cp.restarted"; echo "$(date +%FT%T) restart: REFUSED: main cannot read GitHub: $why; old pane $old left up, next stop retries" | tee -a "$log" >&2; exit 1; }`.
The old pane is the only one holding the context, so it stays, as on a failed create; the marker goes, as there.

**Mid-task line.** One line in `templates/codex-instructions.md` (after line 13) and one in `templates/global-rules.md`
(beside the seat/reviewer rules): when a `gh` read fails mid-task, print on a line of its own
`BLOCKED: GitHub read failed: <command>: <first error line>` and stop; do not go on from a brief's copy of the issue.
Read by `pp_ask_lines` (`scripts/paths.sh:1165`, `^(QUESTION|BLOCKED):`) through `hooks/codex-notify.sh` (Codex seats)
and its twin `hooks/claude-worker-notify.sh` (Claude seats), which always send an ask line to main; main decides to
relaunch or go on. The same edit fixes `templates/codex-instructions.md:10-11`, which says the done line is the only
wake line; a QUESTION: or BLOCKED: line also wakes main.

**Doctor.** `scripts/doctor.sh`, after the review-pass line (~119): group the roles of the resolved routing (not
`codex-reviewer`) by probe, run each against the main checkout; one line per agent and sandbox mode:
- `ok   github read: claude, no sandbox (orchestrator, plan-author, builder, fixer)`
- `ok   github read: codex read-only + network (plan-judge-sol, plan-judge-astra)`
- `FAIL github read: codex read-only + network (plan-judge-sol, plan-judge-astra): no network in the sandbox: error connecting to api.github.com; fix: <per reason>`
The review pass's `--preflight` now runs `review_gh_check`, so its failure prints through the existing `review pass`
FAIL line; on the Codex profile that line says the reads are handed in from the host (the sandbox has none).

**Dispatch guard: no change.** `hooks/codex-dispatch.sh:234` counts a run as read-only only when every turn's
`sandbox_policy` is exactly `{"type":"read-only"}`. A judge now records `{"type":"read-only","network_access":true}`,
so judge panes run every guard, as a write-capable run does. That is the safe side: with network and the owner's gh
credentials a judge can write to GitHub. A pin case records it (section 6).

**Stated authority.** `README.md` beside the `gh` sign-in requirement (~36) and the CHANGELOG entry, one plain line
each: plan judges run Codex with network on and this `gh` sign-in, so they can write to GitHub and reach any host;
the owner accepted that, and every guard still runs in their panes.

## 4. Practice

Fail-fast preflight: followed (one check before every plugin launch, against the seat's own environment and target
repo, loud refusal with the reason, no fallback). Least privilege (read-only network for a read-only seat): followed
for files (writes stay blocked, measured). NOT followed for the network, by the owner's accepted risk: the profile
opens all outbound network (the domain allowlist was measured not to bite), and gh carries the owner's full-scope
credentials, so a judge can write to GitHub (e.g. `gh api --method PATCH .../issues/316 -f state=closed`) and reach
any host. Method limits cannot help: gh's reads are GraphQL POSTs, the same as writes. Stated in README and CHANGELOG;
the guards keep running in judge panes. The Codex reviewer gets host reads handed in, not live sandbox access: its
sandbox is the companion's.

## 5. Catches

- Launch preflight in `seat.sh launch`. Catches: a seat whose sandbox has no network or hides gh's credentials, a seat
  whose own credentials (shellEnv, settings env, Codex home) differ from the host's, a target repo the seat cannot
  read, or a machine not signed in to gh, before the pane opens (the judge that judged from the brief's copy).
- Review-pass check and hand-in. Catches: a review launched with no GitHub read (with or without `Closes:`), a stale
  brief copy (the Codex reviewer gets the live issue, linked issues and PR state), and a reviewer that needed a read it
  did not get (its `BLOCKED:` line refuses the pass).
- Main-restart check. Catches: a /handoff or context restart that would open a main with no GitHub read; the old pane
  stays.
- Doctor line. Catches: the same per agent and sandbox mode, before any unit runs.
- Mid-task `BLOCKED:` line. Catches: a seat that loses GitHub after launch and goes on silently.
