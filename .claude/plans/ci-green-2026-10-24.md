  repo-wide search for the same pattern (`<key>: (...) //` outside tests) finds no other instance. Rejected lazier:
  pin jq 1.8 in CI (the plugin's owners run whatever jq their system has).
- Test 4, collector: rung 2, the cache pattern the file already uses (a JSON file beside `limit-requests.json`,
  written by tmp and `os.replace`, as `requests()` does at `:548-552`): `limit-started.json`, `{transcript path:
  first-line time}`, in the folder of the `cache_path` that `requests()` gets (the `cache_dir` that `seats()` gets).
  - Filled during the existing scan (one open per cycle): in `requests()` (`:458`), a file whose read starts at
    offset 0 (new to the cache, or reset by the truncation check at `:507-508`, size below its offset) notes the time
    of its first line whose `timestamp` parses, the same rule as `started()` (`:1435`). The check goes in the line
    loop (`:519`) before the `"usage"` filter (`:523`) and stops once a time is found. A truncated transcript is
    re-read from 0 by that same check, so its entry is replaced with the new first time: warm and cold reads agree.
    One `shortcut:` comment: a file rewritten to the same or a larger size is missed here as it is by `requests()`;
    key by inode if that ever happens.
  - Written by one helper, `remember_started(cache_dir, times)`: load the memo, merge `times`, drop only paths for
    which `os.path.exists` is false, write by tmp and `os.replace`; on `OSError` skip (a lost memo costs one
    re-open in a later cycle, never a wrong number). Every other live entry stays, so projects that share one
    `CLAUDE_DIR`, and so one request cache (`scripts/dashboard.sh:1081`), never evict each other. `requests()`
    calls it after its own cache write when it noted a time.

    read from offset 0 before this release, or a lost memo write), then stores those times through the same helper.

  entry each).
